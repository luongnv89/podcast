Alice: They call skills one of the building blocks of Uber's software factory. And as usage grows, their focus moves from writing skills to skill quality and evaluation.

Bob: Okay, basics. What actually is a skill?

Alice: A Markdown file that teaches an AI agent to do one job well, like creating a pull request or querying a metrics store. It's like a recipe card: one dish, the steps in order, and a note on when to cook it. On disk, the card is a skill file with a name, a description, and a body of instructions.

Bob: So a recipe box with thousands of cards. Doesn't the agent drown?

Alice: No, because it loads them in three stages. Always loaded: the name and description, about 100 tokens. The body loads only when the skill runs, and scripts and references only when a step needs them.

Bob: Is that Uber's own trick?

Alice: It's the open standard. The Agent Skills specification says agents load skills progressively, pulling in more detail only as a task calls for it, and to keep the main skill file under 500 lines.

Bob: And the description is what the agent reads to decide?

Alice: Exactly. The agent uses the description to decide whether the skill applies, and the spec wants it to say both what the skill does and when to use it. A recipe card with a vague title never leaves the box.

Bob: Where do all those skills even live?

Alice: In one Git repository. Version control already gives each skill an owner, a review, and a history.

Bob: But anyone can write one. How do they stop the junk?

Alice: Three tiers. Picture a restaurant: chalkboard specials any cook can add, the regular menu that's tested and maintained, and the set menu every guest gets. At Uber those are Domain, Core and Always-on, and the expectations for quality rise as a skill graduates.

Bob: Walk me through them.

Alice: Domain: any team can start its own area and publish after one peer approval and a CI check. Core: widely used skills, recommended, tested and maintained by a team, and the platform team reviews every change.

Bob: And what about the Always-on tier?

Alice: About 100 broadly useful skills that are on for everyone, so a new employee has skills on the first run: pull requests, code review, tool access, data analysis, and chat.

Bob: And to move up a tier?

Alice: To graduate a skill, they run their eval system plus a set of quality and usefulness checks. It echoes Hamel Husain's rhythm for evals: cheap ones on every code change, costlier ones on a set cadence.

Bob: Next problem. Engineers don't all use the same agent, right?

Alice: Right, and Uber calls that part of its strategy, because people pick the agent that suits the task. The catch: each agent defines and installs skills differently. Even the open spec warns that support for some fields may vary between agent implementations.

Bob: So you'd package every skill again for each agent?

Alice: That's what aifx avoids, their command-line tool. It's like a universal travel adapter: one plug, any socket. You add a skill or a plugin once, and aifx applies it to whichever agent starts next, Claude Code, Codex or OpenCode.

Bob: And who decides which skills I get?

Alice: Layers. Aifx merges company defaults, a team or program, the repository, the working directory, the user, and a local override. Later layers only add plugins, so a repository can declare the plugins everyone working in it needs.

Bob: With thousands of skills, how do I find the one I need?

Alice: Imagine a library's card catalogue, sorted by what readers actually borrow. Uber has a find-skills skill that finds a quality skill for your workflow, and it ranks skills with evals and run counts into a quality score. You can even ask: "Give me the skills my peers are using that I'm not."

Bob: Why not show the model every tool and let it choose? Maya?

Maya: Tiantian Gan and Qiyao Sun tested that on arXiv, in their RAG-MCP paper. They write that models struggle with a growing number of external tools, due to prompt bloat and selection complexity. Retrieving only the relevant tools first more than triples tool selection accuracy: 43.13 percent versus 13.62.

Bob: So the catalogue beats a pile of books on the floor.

Maya: Exactly. Like a good catalogue, it also cuts prompt tokens, by over 50 percent in their tests.

Bob: And how does Uber know which skills people use?

Alice: OpenTelemetry in agent hooks. Each event records the skill, its version, and whether the agent chose it or the user typed its command, and carries no prompt text and no file contents. Hamel calls logging your traces a prerequisite for human and model-based eval.

Bob: Which brings us to the title. How do you eval a skill?

Alice: It starts with a spec: the skill's goal, its outputs, the tool actions required or forbidden, and the agents and models it targets. Their authoring tool, Skill Workshop, compiles the skill file and its test prompts from that spec, and recompiles them when a model or an agent changes.

Bob: And there's a linter?

Alice: Pass or fail. Steps are numbered with one objective each, and every step checks its result before the next. The skill needs an error recovery table of failures and fixes, where "Try again" doesn't count, and the open spec asks scripts to include helpful error messages too.

Bob: Shame. That's my whole debugging strategy.

Alice: Then the evals. Their guidance is about 5 percent golden cases with a fixed input and expected output, 80 percent real prompts graded on trajectory, and 15 percent judged by the author.

Bob: Trajectory meaning what?

Alice: Picture a driving test. The examiner checks where you parked, but also whether you checked your mirrors in the right order. Trajectory means whether the agent used the right skills and tools in the right order.

Bob: Where do those tests run?

Alice: In three clean setups: Minion, their background agent platform; AES, a managed agent sandbox; and devpods, remote development machines. The clean room catches skills that expected certain file paths, cached documents, or certain OS tooling.

Bob: The classic "it works on my machine".

Alice: Then a surprise: evals that pass 70 to 90 percent of runs can be more useful than ones that pass 100. Hamel Husain says it in "Your AI Product Needs Evals" too: you don't necessarily need a 100 percent pass rate, it's a product decision.

Bob: Why would a perfect score be bad?

Alice: A 100 percent pass rate may mean an eval is missing meaningful changes in the answer. Answers vary, and judges can too.

Bob: And who's the judge?

Alice: Often an LLM, but Uber says LLM-as-judge works best with a human-annotated set that authors grade repeatedly. Hamel's advice matches: track the correlation between model-based and human evaluation, to decide how much you can rely on the automatic one.

Bob: That rings a bell from our Factory Engineering episode with Ben Holmes, where another agent reviews past agent conversations to score them.

Alice: Same idea, and Uber adds the human anchor. On their own, they warn, agents can miss a significant hallucination when the answer otherwise follows the expected format.

Bob: Does a skill always help, though?

Alice: They test that with ablation. They replay real prompts once with the skill and once without, and a blind judge picks the better answer. In a majority of cases, skills made the session more successful and cost less.

Bob: Give me a number.

Alice: Their warehouse query skill. Without it, sessions made 13 percent more tool calls, had six times as many tool errors, and took 31 percent longer. And the answer with the skill won 87 percent of the comparisons.

Bob: Six times the errors. Ouch.

Alice: But as models get better, more words can reduce performance, so they also test removing words. Lena, SkillsBench looked at this from outside?

Lena: It did. Xiangyi Li and colleagues on arXiv built SkillsBench: 87 tasks across 8 domains, run with and without curated skills. Curated skills raised the average pass rate from 33.9 percent to 50.5.

Bob: So skills work. Does size matter?

Lena: Focused skills with at most three modules outperform larger or exhaustive bundles. It's like a pocket checklist versus the full manual: the one you actually read wins. And smaller models with skills can match larger models without them.

Bob: But a skill isn't free either?

Alice: No. It's like packing for a hike: everything you put in the backpack, you carry up every hill after. A skill's instructions, tool calls and results enter the context, and every later turn in the session pays for that context again.

Bob: How do they even measure that?

Alice: Agents keep a running total of the session's cost. They take the last total before the skill call and the first one after, subtract, and average per invocation.

Bob: And how do they cut it?

Alice: Use code over LLMs for steps that never vary. And run the skill in a worker on a cheaper model: the big tool result stays in the worker, and a tracing skill's cost per invocation fell 46 percent.

Bob: Okay, what else is on the list?

Alice: Run a small script when the skill loads: one search skill went from four turns to three, and its mean cost fell 32 percent. And move polling out of the main session, because in their 20 highest-spend sessions, notification turns were about a third of the spend.

Bob: A third of the bill on "are we there yet?"

Alice: Tool servers were worse: with more than 100 tools, definitions took 50,000 to 70,000 tokens before the user typed anything. That's the prompt bloat Maya's paper warned about. Inspired by Cloudflare's Code Mode, Uber moved those flows into scripts that call tools through a gateway.

Bob: Now my favourite part. Agents report their own bugs?

Alice: They do. A skill can stop working for a thousand reasons: a model upgrade, a tool changing its flags, a harness change. And an agent knows when it's struggling, say after 100 turns fighting some weird error.

Bob: So what does it do about it?

Alice: It's like the warning light on a car's dashboard: the car can't fix the engine, but it tells you something's wrong. Every agent has log-papercut, an always-on skill, and reports what it tried, what it expected, what happened, and what would fix it. All reports go to one dashboard, grouped by skill.
